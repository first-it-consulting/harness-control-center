# ADR-0015: Agents call A2A agents through their proxy

- Status: accepted
- Date: 2026-10-26

## Context

The Agent2Agent protocol (A2A) lets an agent hand work to agents others
run. That sends the user's data to someone else and brings back
untrusted answers, so it has to be granted, visible and, where wanted,
approved per message.

## Decision

- **Peers are named.** `spec.a2a.agents` lists them by name and https
  URL (their JSON-RPC endpoint). Their hosts must be in the egress
  allowlist; a credential for a host is added by the broker. Nothing
  else is reachable, A2A or not.
- **A client in the image.** `hcc-guest a2a list|card|send|get` talks to
  exactly these agents, through the proxy, trusting the job CA. Init
  tells the agent about it. Answers are printed as data.
- **Gates per message.** `approvals.requireFor` accepts `a2a.<agent>.send`
  (`message/send`, `message/stream`), `a2a.<agent>.cancel` (`tasks/cancel`),
  `a2a.<agent>.read` (everything else), and the groups `a2a.<agent>` and
  `a2a`. The proxy then reads every request with a body to such a host,
  whatever its path, as strict JSON-RPC (ADR-0014's rules: valid UTF-8, no
  duplicate or case-variant keys, no encoded bodies), and shows the full
  call (over 2 KiB is refused).
- **No inbound A2A.** Harnesses are not exposed as A2A agents: runners
  accept no connections (ADR-0003).

## Consequences

- Talking to agents that stream (`message/stream`) works through the
  proxy like any HTTPS response; gating applies to the request.
- What a peer does with a message is outside this system; the
  explanation says so.
